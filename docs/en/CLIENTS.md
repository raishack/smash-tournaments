# Build your branded apps

[Back to the project](../../README.md) · [Branding first](BRANDING.md)

Run the configuration script before building. Each operator supplies their own app IDs, domain, signing credentials and optional push configuration. Sample IDs are for evaluation, not shared production identities.

## Android management and Players

Requirements: Android SDK with platform 36, build tools, JDK 21, and the checked-in Gradle wrapper. The management/player apps support Android API 26+.

Set `ANDROID_HOME` and `JAVA_HOME`, or configure your SDK through Android Studio. On Windows use `android/gradlew.bat`; on Linux/macOS run the wrapper with `sh` if its executable bit is not preserved.

```bash
sh android/gradlew -p android :app:testDebugUnitTest :app-player:testDebugUnitTest
sh android/gradlew -p android :app:assembleRelease :app-player:assembleRelease
```

APK output directories:

- `android/app/build/outputs/apk/release/`
- `android/app-player/build/outputs/apk/release/`

### Signing

Create your own keystore and ignored `android/keystore.properties`:

```properties
storeFile=/private/path/your-release.jks
storePassword=YOUR_PRIVATE_PASSWORD
keyAlias=your-release-alias
keyPassword=YOUR_PRIVATE_PASSWORD
```

Keep the keystore backed up privately. Current Gradle configuration falls back to debug signing if no release keystore exists; that is useful for local validation but **do not distribute debug-signed builds**. Inspect the APK certificate before publishing updates. Preserve application IDs and signing keys across releases.

Players builds without Firebase configuration. To enable remote push, add your actual `google-services.json` for the configured Players application ID. Validate start.gg sign-in and notifications on a physical device.

## Windows desktop management

Build the MSI on Windows with JDK 21 and the packaging prerequisites required by the Compose/Java packaging toolchain (including WiX for MSI). The runtime is bundled with the installer.

```powershell
.\android\gradlew.bat -p android :desktop:test :desktop:packageReleaseMsi
```

Look under `android/desktop/build/compose/binaries/main-release/msi/`. Packaging also runs `checkPackagedRuntime`: it exercises login/session serialization using the reduced JVM shipped to users. Keep the explicit `jdk.unsupported` module; a successful developer-JDK test alone does not verify the packaged runtime.

Configuration sets package name, icon, vendor and Windows UpgradeCode. Keep that UUID stable for future upgrades. Review version in `android/desktop/build.gradle.kts` and follow [Updates](UPDATES.md) before distributing.

Linux DEB/RPM packaging targets exist, but the primary desktop release workflow here is Windows. Validate Linux packaging and platform-specific session behavior yourself before distributing those targets.

## iOS management and Players

Requirements: a Mac, Xcode with the iOS SDK, and [XcodeGen](https://github.com/yonaskolb/XcodeGen). The generated projects target iOS 17+ and iPhone/iPad. Apple signing/store distribution requires your own developer account.

Run configuration first, then on your Mac:

```bash
(cd ios-manage && xcodegen generate)
(cd ios-player && xcodegen generate)
open ios-manage/TournamentManager.xcodeproj
open ios-player/TournamentPlayer.xcodeproj
```

These commands keep your shell at the repository root.

For each target:

1. Select your team under **Signing & Capabilities**.
2. Confirm the bundle identifier and display name match your branding file.
3. Confirm `BrandAssets.xcassets` supplies the `AppIcon` set.
4. Confirm the configured callback scheme under URL Types.
5. Run a simulator build, then test a real device and sign-in/session restoration.
6. Set your own marketing/build versions, archive a Release build and distribute using Xcode/App Store Connect.

Unsigned CI-style validation:

```bash
xcodebuild -project ios-manage/TournamentManager.xcodeproj -scheme TournamentManager -sdk iphonesimulator -configuration Debug CODE_SIGNING_ALLOWED=NO build
xcodebuild -project ios-player/TournamentPlayer.xcodeproj -scheme TournamentPlayer -sdk iphonesimulator -configuration Debug CODE_SIGNING_ALLOWED=NO build
```

Generated projects use Swift sources and the generated asset catalogs. They do not modify any pre-existing Xcode project. `project.yml` is regenerated by branding configuration; preserve any custom changes or extend that specification before regenerating an Xcode project.

### Optional iOS remote push

Add Firebase's Swift packages from `https://github.com/firebase/firebase-ios-sdk`, selecting `FirebaseCore` and `FirebaseMessaging` for Players. Add your own `GoogleService-Info.plist` to the target. Enable Push Notifications and Background Modes → Remote notifications, configure APNs in Firebase and use compatible signing profiles.

The source conditionally imports Firebase. The generated baseline project works without it; adding Firebase requires updating your project specification if you intend to regenerate it. Management does not need Firebase.

## Before any release

Test your own real URL, account sign-in, restart/session restoration, orientation changes, fullscreen actions, notifications and update installation. A successful unsigned build does not mean an app is signed, uploaded to Apple or installed on a device.
